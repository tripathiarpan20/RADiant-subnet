## The manifest

`manifest_hash` is sha256 over canonical JSON (sorted keys, no whitespace) of
the normalised pin set. Normalisation is total: every key is filled with its
default, numbers get one type, and lists whose order means nothing are
sorted. A minimal manifest file and the fully spelled-out fixture therefore
hash the same. A default changed later can't move the hash of a stored
campaign, because the stored copy holds the value it was hashed with.

| Pinned (in the hash) | Outside the hash |
| --- | --- |
| `campaign_id` (2 to 24 chars, the cap the HF pin name leaves) | `title` |
| `labels` | `submission_fee` (then block-effective, append-only history) |
| `solution`: base class, SDK version, solution format | `visibility`: reveal policy and fast reveal |
| `data_pool`: DataHive v1, countries, which certainties count as positive | `status` |
| `hardware`: GPU allowlist, CPU and memory caps | |
| `limits`: zip and unzipped caps, weights cap, image cap, build, model-load and eval timeouts | |
| `harness`: uint16 input, max batch size, 3-decimal rounding | |
| `rounds`: round size, max wait, sample size, per-label quotas | |
| `scoring_rule`: metric, quality curve, quality/speed/cost weights, label weights, epsilon | |
| `gates`: obfuscation rule set, and the weight formats g5 accepts (safetensors only) | |
| `emission_rule`: Pareton's `linear_decay` | |

The validators reject unknown keys anywhere, a curve that is steeper above the
knee than below it, weights that don't sum to 1, label weights that miss a
label, and quotas larger than the round. The seed CLI warns when speed plus
cost weight could let an all-negative model beat a working one. The quality
curve reproduces the plan's table (0.6 → 0.27, 0.8 → 0.80, 0.9 → 0.95, 0.95 → 0.99).

## What the database enforces

Each of these holds even against manual SQL:

- A manifest is frozen once its campaign leaves `draft`.
- Status moves only from `draft` to `open` or `archived`, from `open` to
  `closed`, and from `closed` to `open` or `archived`.
- Fee history is append-only, starts at block 0, grows by block, and every
  amount is a whole number of RAO.
- The open campaigns' emission start weights sum to at most 1. This is
  Pareton's trigger, with an advisory lock added so two campaigns opening at
  once can't both pass.
- The stored `manifest` must name the row's own `campaign_id`.

## Choices to review

1. **MinIO comes from Chainguard, not MinIO.** MinIO stopped publishing
   official images in October 2025, and `minio/minio` has since gone from
   Docker Hub and Quay. The stack uses `cgr.dev/chainguard/minio`, pinned by
   digest. It is free, multi-arch and built from MinIO's source
   (RELEASE.2026-11-23). The alternatives are the `pgsty/minio` community fork
   or building from source. MinIO is AGPLv3, which is fine for running it
   unmodified.
2. **`campaign_id` is a short slug, not a UUID as in Pareton.** It goes into
   the HF pin name `rad-<campaign>-<hotkey>-s<id>`, which caps it at 24
   characters.
3. **Reveal defaults to `public_after_reveal` after 48 h.** Pareton defaults to
   private, but RADiant reveals every evaluated submission. The fixture sets a
   fast reveal at leader quality below 0.5 with a 6 h delay; those two numbers
   are my picks.
4. **F-beta's default knee is 0.6, not 0.8.** With a chance level of 0, a knee
   at 0.8 makes the curve steeper above the knee than below it, which the
   validator refuses. AUROC keeps 0.8.
5. **The fixture's fee recipient is the public dev key Alice.** That's for
   local runs only. Seed testnet with `RADIANT_FEE_RECIPIENT` set to the owner
   coldkey; the fee is outside the hash, so the hash doesn't change. This is
   tracked in `TODO.md`.
6. **Fixture labels are tuberculosis, silicosis, pneumonia and fibrosis,** the
   four conditions in the demo data.
7. **A first slice of the API landed early** (`/health` and campaigns), so
   Caddy has something to serve and the exit gate can read the hash over
   HTTP. The rest of the API is R8.
8. **Least privilege is partial.** The app services use the database owner
   role for now; per-service roles come with the services that need them (R3
   and R4). Adminer is bound to localhost and operators log in as the
   read-only role, which can only `SELECT` and runs read-only transactions by
   default. Nothing stops someone with the owner password from logging in
   through Adminer, so keep that password off operator machines.
9. **MinIO's S3 port is published on 127.0.0.1 only.** Miners need to PUT to
   presigned URLs, so R3 puts it behind Caddy on its own domain.

## Running it

```bash
cp .env.example .env    # set POSTGRES_PASSWORD, RADIANT_DB_READONLY_PASSWORD, MINIO_ROOT_PASSWORD
docker compose up -d --build
curl -s localhost:8080/v1/campaigns?include_drafts=1
```

- **Adminer:** http://127.0.0.1:8081. Use server `postgres` and user
  `radiant_readonly` with `RADIANT_DB_READONLY_PASSWORD`. On the VPS, reach it
  with `ssh -L 8081:127.0.0.1:8081`.
- **MinIO console:** http://127.0.0.1:9001.
- **Opening a campaign:** `docker compose run --rm init python -m campaign.set_status testnet-cxr-01 open`.
- **Exit gate:** `scripts/r1_exit_gate.sh` runs under its own compose project
  with random passwords and ports, and removes its containers and volumes
  afterwards.
- **Tests:** `uv run pytest`. The database tests start a throwaway Postgres
  container; set `RADIANT_TEST_DATABASE_URL` to use your own.
