override fails with the same reason code the validator would give.

## How a solution is checked

The harness runs `qualify` (gate g8) on a public warmup set: 8 synthetic,
deterministic 12-bit images at real X-ray sizes, including non-square ones.
No real patient or DataHive data is involved, so the whole log can be shown to
the miner. The checks and the codes each one gives:

| Gate | Checks | Codes |
| --- | --- | --- |
| g1 size | Zip size cap from the manifest | `ZIP_TOO_LARGE`, `ZIP_INVALID` |
| g2 archive | No path escape, symlinks, nested archives or binary files; at most 200 files; the uncompressed cap is enforced while inflating, not taken from the header; only the allowed files | `PATH_ESCAPE`, `SYMLINK`, `NESTED_ARCHIVE`, `OPAQUE_BINARY`, `TOO_MANY_FILES`, `UNZIPPED_TOO_LARGE`, `UNEXPECTED_FILE`, `MISSING_FILE` |
| Descriptor | Base class, SDK version, GPU in the allowlist, CPUs and batch size within the manifest | `BASE_CLASS_MISMATCH`, `SDK_VERSION_MISMATCH`, `GPU_NOT_ALLOWED`, `CPUS_OVER_LIMIT`, `BATCH_SIZE_INVALID` |
| `.env` | Only `HF_REPO_ID`, `HF_REVISION` (a full 40-character sha) and `HF_TOKEN` | `ENV_UNKNOWN_KEY`, `ENV_BAD_REVISION`, `ENV_BAD_REPO` |
| Lockfile | Every line `name==version` with sha256 hashes; no indexes, URLs, paths or includes | `LOCK_UNPINNED`, `LOCK_MISSING_HASH`, `LOCK_FORBIDDEN_OPTION` |
| g3 contract | By AST, without importing: exactly one subclass overriding all five methods. Network and process modules are banned, including literal `importlib.import_module` and `__import__` calls | `CONTRACT_*`, `BANNED_IMPORT`, `SYNTAX_ERROR` |
| g5 weights | The revision resolves to itself, total size is under the cap, and every LFS file matches | `HF_*` |
| g7 build | Base image, then `pip install --no-deps --require-hashes` of the lock, then the SDK, the code without `.env`, and the weights | `BUILD_FAILED`, `BUILD_TIMEOUT` |
| g8 qualification | Offline sandbox on the solution's GPU; the clock runs from the miner module's import until `load_model` returns; outputs are exactly the labels, each in [0, 1] | `IMPORT_FAILED`, `INIT_FAILED`, `LOAD_TIMEOUT`, `LOAD_CRASH`, `EVAL_CRASH`, `EVAL_TIMEOUT`, `BAD_OUTPUT` |
| Capacity | No GPU free within `--gpu-wait` (15 min by default). This is infrastructure: it exits with status 4, is never a rejection, and Modal doesn't bill while a sandbox is queued | `GPU_UNAVAILABLE` |

## Choices to review

1. **`HF_TOKEN` is optional.** A public weights repo, like the reference
   miner's, needs no token. Private repos still need a fine-grained read-only
   token, and R4 runs the private-download checks.
2. **SDK 1.0.0 fixes the base image:** Python 3.12, torch 2.5.1, torchvision
   0.20.1, numpy 2.2.6 and pillow 11.3.0, all hash-pinned. A miner's lock
   adds only what the base lacks. It is installed with `--no-deps`, so the
   lock must be complete; `scripts/lock_reference_miner.sh` shows how to
   generate one with uv.
3. **The reference miner unpickles its weights.** `model.pt` in the public
   repo is a pickled torchxrayvision module, so it is loaded with
   `weights_only=False`. That runs only inside the offline sandbox, and the
   network rebuilt from it matches torchxrayvision's own loader exactly. Its
   descriptor asks for an L4, 4 CPUs and batches of 32.
4. **The warmup set is synthetic.** Real public X-rays (for example NIH
   ChestX-ray14) would make a nicer smoke test, but they need a licence check
   first. Qualification only tests that the model runs and returns
   well-formed outputs, so synthetic images are enough.
5. **Validation memory is a range.** The SDK asks Modal for 4 GiB up to the
   manifest's `max_memory_mib`, so a small model isn't billed for 32 GiB.
6. **The harness's result line is trusted for the self-test only.** Miner
   code shares the harness's process, so in principle it could print its own
   result line. That can only affect the miner's own report. R4 times load and
   evaluation from outside the sandbox and doesn't rely on that line for
   anything a miner could gain from.

7. **GPU capacity is a real constraint.** The first L4 qualification waited
   167 s for a GPU. A rerun queued for more than 15 minutes until I stopped
   it, which is what led to the `--gpu-wait` cap. A miner who hits it can
   retry or pick another allowed GPU (the campaign allows L4 and L40S). R4 and
   R6 must treat the same wait as infrastructure.

## Running it

```bash
uv sync --extra sdk --extra validator --extra dev
cp -r radiant_sdk/reference_miner my-miner && cp my-miner/.env.template my-miner/.env
uv run radiant-sdk prepare my-miner --out build
uv run radiant-sdk validate build/solution.zip --campaign testnet-cxr-01 --api-url http://localhost:8080
uv run radiant-sdk submit build/solution.zip --campaign testnet-cxr-01 --api-url http://localhost:8080
scripts/r2_exit_gate.sh --api-url http://localhost:8080      # add --static-only to skip Modal
```
