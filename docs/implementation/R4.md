## States

```text
pending -> gating -> identity_ok -> fetched -> static_ok -> weights_ok -> stripped
        -> unique -> built -> qualified -> pinned -> queued
                  -> rejected (reason_code)  |  rejected_duplicate  |  infra_failed
```

- **Infrastructure failures are never the miner's fault.** These are: no GPU
  within `SANDBOX_GPU_WAIT_S`, a sandbox that won't start, a Modal or storage
  error, or a validator bug (`WORKER_ERROR`). The submission is requeued once,
  after `RADIANT_INFRA_RETRY_AFTER_S` (15 min). Its scratch directory is kept,
  so the retry still has the original zip and the weights. A second
  infrastructure failure is terminal until an operator requeues it, as in
  Pareton.
- **A leader infra failure voids the round.** That part is R6.
- **The miner's HF token is used once.** After g5, the stored zip is replaced
  by a copy without `.env`, checked against `code_sha256`. A rejected
  submission's zip is stripped the same way, or deleted if it can't be read.
  The worker's scratch copy is deleted when the submission settles.
- **Only data-free logs are kept for miners:** the build log and the
  qualification log. Neither sandbox has evaluation data mounted.

## Findings and choices to review

1. **Modal scheduling is the weak point, not GPUs as such.** On 27 Nov, L4
   sandboxes queued for 15+ minutes several times. Then one L40S
   qualification sandbox sat unscheduled while fresh requests with the same
   spec started in 4 s, and `Sandbox.create` blocked the whole time.
   - Qualification now creates sandboxes in a thread, and cancels and re-asks
     after 2 minutes without a start.
   - Campaigns now allow L40S and T4 only (decided 27 Nov), and the reference
     miner asks for T4.
   - In this run, T4 sandboxes started in 2 to 6 s.
2. **The duplicate rule is the plan's:** same `code_sha256` and same weights.
   A one-character change to `model.py` with copied weights passes g6. Catching
   that needs weights-only matching, or a similarity check. This is deferred
   to a later milestone (decided 27 Nov).
3. **The image size cap is unattested,** as in vidaio. Modal doesn't report
   image sizes, so `image_cap_gb` is enforced only indirectly, through the
   build timeout and the weights cap (g5).
4. **The R0 Hugging Face checks:**
   - Private download with a fine-grained token is covered by code, but
     hasn't been run against a private repo. The reference weights are public.
   - The org quota has no API. The billing page shows 100 GB of private
     storage on the free plan, with 0 GB used on 27 Nov.
5. **Validator Modal credentials.** The worker container reads
   `MODAL_TOKEN_ID/SECRET` from `.env`. The gate ran on the host with the
   `modal setup` login instead. Set the token before running `docker compose
   up` with the worker.

## Running it

```bash
scripts/r4_exit_gate.sh                 # needs HF_PIN_ORG/HF_PIN_TOKEN and the RADIANT_S3_* bucket in .env
R4_KEEP_PIN=1 scripts/r4_exit_gate.sh   # keep the test pin
docker compose up -d --build            # local dev/CI stack (needs MODAL_TOKEN_* in .env)
```

## Post-R4 updates (28 Nov 2026)

Following the R0–R4 review and production-readiness work:

- **Least-privilege Postgres roles & Neon DB support:** `db/migrate.py` now provisions per-service roles (`radiant_api`, `radiant_watcher`, `radiant_worker`, `radiant_readonly`), supports `--grants-only` for managed Postgres (Neon) where `neondb_owner` cannot run `CREATE ROLE`, and rejects pooled URLs (`-pooler.`) because migrations use session-level `pg_advisory_lock`. `db/connection.py` automatically sets `prepare_threshold=None` for `-pooler.` / `pgbouncer=true` URLs so runtime services work cleanly over Neon's transaction pooler.
- **Portable native `systemd` deployment:** Added `ops/systemd/radiant-{api,watcher,worker}.service`, `ops/systemd/caddy-override.conf`, `ops/systemd/env/*.env.example`, `ops/install_systemd.sh`, `ops/README.md`, and parameterized `Caddyfile` (`{$RADIANT_API_UPSTREAM:api:8000}`). This runs identically on Hippius AMD SEV-SNP Confidential VMs, regular cloud VMs, and bare-metal hosts (with optional `tmpfs` scratch recommended on CVMs). `docker-compose.yml` stays strictly for local dev and CI.
- **Next (R4.5):** Earlier R2–R4 exit gates ran locally on macOS against throwaway Docker Postgres and local `modal setup` logins (see Finding #5 above). R4.5 validates the full production topology end-to-end on a **Hippius Confidential VM** provisioned via the Hippius Compute API, backed by real **Neon Postgres** credentials, **Hippius S3**, `systemd` + Caddy, and a live base-miner run using explicit `MODAL_TOKEN_ID`/`MODAL_TOKEN_SECRET`.
